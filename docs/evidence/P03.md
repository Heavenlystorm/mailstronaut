# P03 evidence (partial, 2026-10-27)

This is an initial persistence experiment, not milestone completion or an API
ready for synchronization integration. The first `rusqlite_migration` migration
creates a provisional schema, enables foreign keys and WAL, and uses bundled SQLite
with FTS5. The concrete `Store` opens a caller-supplied data directory; it is not
an XDG locator or a bounded database worker. Blob writes use SHA-256, a sibling
temporary file, file sync, rename and directory sync; orphan collection is only
safe when serialized with blob writes and reference commits. The current API does
not yet provide that atomic ingestion operation. Cache clearing retains draft,
outbox and reminder rows but currently removes all message and analysis rows;
reconciliation of user-owned message references remains unresolved.

Local `nix develop --command bash ci/check.sh` passed: two synthetic tests check
migration/reopen and foreign keys, and blob deduplication/orphan cleanup plus
preservation of draft/outbox/reminder rows. This is not a crash-injection test.
No 100k benchmark, old-schema upgrade, migration failure/rollback, corruption UX,
UID invalidation, FTS purge/pagination, MIME, threading, or mail synchronization
validation was performed. The schema omits many required fields and has no CRUD
interface for ingestion or user-owned state; it must be revised before use. No
CI, GUI, live account, or distribution acceptance is claimed.
